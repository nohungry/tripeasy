## 0. 目的

讓會員中心可以從前端完整操作：查看所有狀態的訂單（待付款的可以繼續付款）、查看點數紀錄與等級、管理通知設定、收藏行程。同時修掉 P1 以來一直擋在「對外開放」前面的越權讀取問題（契約 §4.2 (c)）。過程照 P2–P4 的慣例寫成教學報告。

**P5 主線 E2E**：登入 → 搜尋結果卡片按愛心收藏 → 收藏頁看到該行程 → 進入行程頁購買並付款（沿用 P4 流程）→ 我的訂單看到「已付款」與明細 → 點數紀錄看到購物回饋 → 收藏頁取消收藏。

## 1. 範圍

### 要做（goals）
1. **我的訂單**【使用者定：B】：列出所有狀態的訂單（待付款、付款進行中、已付款、逾時、已取消、已退款），可以看明細，待付款的訂單可以「繼續付款」，導向 P4 的付款頁。同時修掉越權讀取。
2. **點數與等級**【使用者定：A】：
   - 新增唯讀的點數紀錄 API 和頁面。
   - 會員等級分頁顯示目前等級、點數餘額和可用的優惠券。
   - 等級維持 seed 的值，不實作升級。
3. **通知設定**【使用者定：A】：
   - 前端表單接上現有的 3 支 API，補上驗證和唯一約束。
   - 只儲存設定，不實際寄送通知。
4. **收藏**【使用者定：A】：
   - 收藏頁可以列出、取消收藏、點進行程頁。
   - 行程頁和搜尋結果卡片加上愛心，可以收藏或取消。首頁的靜態愛心也接上，或者改成和卡片共用同一個元件。
   - 後端加上唯一約束，重複收藏時回傳原本那筆；商品 API 回傳 `favorite_id`。
   - 修掉收藏列表回傳兩次回應的問題，以及格式錯誤的 id 回 500 的問題。
5. **姓名規則統一**【使用者定：A】：
   - 註冊、會員資料、結帳收件人共用同一套規則：2 到 20 個字。
   - Google 登入時，名字超過 20 字就截斷到 20 字。
6. **P4 留下的項目**（§7）。

### 不做（non-goals）
- **會員手動取消訂單**【使用者定】：留到 P6，和後台的訂單管理一起做。
- **會員等級升級規則**【使用者定】：留到 P6 的後台會員管理再決定。報告裡寫明「升級規則未實作」。
- **實際寄送通知、站內通知、價格追蹤比對**【使用者定】：屬於 P6 的排程。
- **還原促銷勾選框**【Claude 定】：不做 — 後端沒有對應的欄位，勾了也沒有作用 — 若錯，P6 要另外加欄位和 UI。報告把這項寫成結案。
- **Facebook 登入的空路由（`routes/userinfo.js:19`）**【Claude 定】：不動 — 和 P5 無關 — 若錯，代價只是殘留一個死路由。

### 反目標（做了也算失敗）
- 會員能讀到別人的訂單、點數或收藏（任何會員端點都不行）。
- 會員中心的任何地方顯示負的點數。
- 新增的程式違反 `docs/lock-order.md` 的上鎖順序，或是新增了交易路徑卻沒有寫進那份文件。
- 為了讓測試變綠而改掉測試的斷言，卻沒有修正底層的程式。

## 2. 做法（approaches）

**採用：按功能逐塊完成**【使用者定】。順序如下，每一塊都從後端、前端做到 E2E 再進入下一塊，審查也一塊一塊審：
1. 地基（migration、共用規則）
2. 我的訂單
3. 點數與等級
4. 通知設定
5. 收藏
6. 清理（§7）

**沒採用：先做完全部後端，再做全部前端。** 這種做法要到最後才能跑 E2E，問題會累積到後期才浮現。P4 用的也是逐塊完成，效果不錯。

## 4. 後端

### 4.1 共通
- 所有新增或修改的會員端點都要加上 `authRole('User')`（總 spec :156）。收藏的 POST 和 DELETE 目前缺這一層（`routes/collection.js:14`、`:17`，讀碼推定）。
- 驗證錯誤一律經過 `utils/Validator/joiMessage.js` 的 `userMessage()`，並把新增的 middleware 加進 `tests/test_validator_sweep.py` 的來源掃描清單。
- 擁有者檢查放在 SQL 條件裡（`WHERE ... AND user_id = $me`），查不到就回 404 和中文訊息，不要先查出資料再比對擁有者。
- 新增的交易路徑一律寫進 `docs/lock-order.md`。P5 新增的端點原則上都是唯讀，沒有交易；例外是 §4.5 的收藏新增，以及 §7 修改到的既有交易。

### 4.2 我的訂單
- **`GET /api/v1/user/orders`**（新增）：
  - 列出本人的所有訂單，每筆包含：訂單編號、建立時間、狀態（數字和中文名稱）、原價總額、應付金額、折扣類型與金額、品項數、第一個品項的行程名稱和圖片。
  - 應付金額一律用 `computePayable`（P4 GC12）計算，不直接讀 `orders.discount_price`。
  - 排序方式是建立時間新到舊，支援分頁（`page`、`limit`，預設值比照購物車列表）。
  - **狀態對應**【Claude 定】：`orders.payment_status` 的值定義在 `utils/trade.js:3`，和契約 :903 一致。
    - `-1`（剛建立）和 `0`（已填寫、未付款）都顯示為「待付款」。
    - 如果 `paymentInProgress()`（`trade.js:147-153`，依據 `payment` 表即時判斷）成立，改為顯示「付款處理中」。列表 SQL 用相同條件的子查詢算出來，不要逐筆呼叫函式。
    - `1` 顯示「已付款」，`2` 顯示「已取消」，`3` 顯示「已退款」，`4` 顯示「已逾時」。
    - 理由：「付款進行中」沒有對應的資料庫欄位。
    - 若錯的代價：只是顯示文字不同。
  - **期限**：回應多帶一個 `deadline` 欄位，值為 `created_at + ORDER_PAYMENT_TIMEOUT_MINUTES`，計算方式要和 `trade.js:136-137` 共用同一個函式。前端不要自己算。
  - **讀取不寫入**【Claude 定】：讀取路徑不鎖訂單，也不把逾時的訂單寫成 4。待付款的訂單如果已經超過 `deadline`，前端顯示「已逾時」，也不提供「繼續付款」。理由：列表會被頻繁讀取，如果在這裡寫入，就會和 notify 互相排隊。若錯的代價：資料庫裡的狀態要等到下一次寫入路徑（summary 或付款）才會變成 4。
- **`GET /api/v1/user/orders/:order_id`**（新增）：回傳單一訂單的明細，包括品項、收件資料、折扣，以及付款紀錄的摘要（時間、結果；不回傳藍新的原始欄位）。不是本人的訂單一律回 404 `查無此訂單項目`，和 P4 的訊息一致。
- **既有的 `/user/purchases/info` 和 `/info/:order_item_id`**【Claude 定】：
  - 決定：修掉越權讀取（`middlewares/purchases/index.js:31`、`controllers/purchases.js:59`）和不會觸發的 404（`:34`），並加上越權測試；前端改用新的 API。舊端點保留，不刪除。
  - 理由：契約 §4.2 (c) 要求修好才能對外開放；刪除會讓現有的 smoke 測試失效。
  - 若錯的代價：多維護兩支端點。
- 「繼續付款」：`-1` 和 `0` 的訂單，只要還沒超過 `deadline`、也沒有付款正在進行，前端就導向 P4 的付款頁 `pay.vue`，不需要新的後端 API。（讀碼推定）`pay.vue` 本身就負責填寫收件資料，這一步會把 `-1` 推進成 `0`；計畫的第一步要先驗證 `-1` 訂單進入 `pay.vue` 後，可以把收件資料填完。若驗證結果不成立，就停下來回報。「付款處理中」的訂單不提供這個按鈕。

### 4.3 點數與等級
- **`GET /api/v1/user/points/records`**（新增）：
  - 列出本人的 `point_record`，每筆包含：時間、變動量（帶正負號）、原因（中文）、關聯的訂單編號。
  - 排序方式是新到舊，支援分頁。
  - **原因對應**【Claude 定】。資料庫實際寫入的值見 `trade.js:309、337、346、404、410`，對應方式如下：
    - `新增` → 購物回饋
    - `減少` → 點數折抵
    - `退款收回` → 退款收回回饋
    - `退款退回` → 退款退還折抵
    - 其他沒列到的值，原樣顯示。
  - **`減少_確認中` 不列出**【Claude 定】。它是付款還沒完成時的預扣紀錄，付款成功後會轉成 `減少`，逾時或取消時會釋放。若把它也列出來，會員會看到一筆之後消失的紀錄。若錯的代價：會員看不到正在保留中的點數；結帳頁本來就會顯示可用點數。
  - **餘額以 `user_level.travel_point` 為準**，負數顯示為 0。點數紀錄只是明細，不保證加總後等於餘額，因為 seed 的初始點數沒有對應的紀錄。頁面上要註明這一點。
- **`GET /user/userinfo/pointslevel`**（修改，`controllers/userProfile.js:123-178`）：
  - 點數餘額小於 0 時回傳 0；資料庫裡存的值不變【使用者定：負點數一律顯示 0；Claude 定：在後端處理】。
  - 沒有優惠券時，`coupon` 回傳空陣列，不再回傳欄位全是 null 的物件。
  - `tests/test_api_smoke.py:282-291` 斷言的是錯誤行為，要同步改掉。
- **會員等級**：顯示 seed 的等級名稱與回饋比例，不實作升級。

### 4.4 通知設定
- 現有 3 支 API（`routes/automation.js`）保留。修改項目如下：
  - 只要會員沒有 `auto_setting` 的資料，讀取時就回傳預設值；寫入改成 upsert，搭配 §3 的唯一約束。
  - 價格追蹤的 `country`／`region` 改成驗證「必須是系統裡存在的值」，來源用 P3 的地區資料。
  - 數字型態的開關（SMALLINT）在 API 輸出時轉成布林值。前端要同步配合，計畫階段要確認沒有其他呼叫者。
- 補上 API 測試，涵蓋：正常、驗證、未登入 401、admin 被擋、upsert 的冪等性。

### 4.5 收藏
- **列表**：修掉回傳兩次回應的問題（`controllers/collection.js:39-46` 與 `:57-64`），並移除 `tests/test_api_smoke.py:365-376` 用 `Connection: close` 繞過問題的寫法。
- **新增 `POST /user/collection/info/:tour_id`**：
  - 先驗證 `tour_id` 必須是 UUID，格式錯誤回 400（`tests/test_async_errors.py:14` 原本斷言 500，要改掉）。
  - 行程不存在或已下架回 404。
  - `INSERT ... ON CONFLICT (user_id, tour_id) DO NOTHING`，再查出那筆資料，**重複收藏回 200 和原本的 `favorite_id`**，第一次收藏回 201。
- **刪除**：維持用 `favorite_id` 刪除。
- **商品 API**：凡是回傳 `is_favorited` 的地方，都多回一個 `favorite_id`，沒有收藏時為 `null`。
  - 涉及的程式：`controllers/product.js:295`、`:370`、`:461`。
  - `is_favorited` 的值來自 `backend/migrations/R__views_functions.sql` 裡 4 個 view 的 `EXISTS`（:112、:223、:326、:428）。這 4 個 view 都要一起改，屬於 P5 範圍，契約要同步更新。
- **下架行程的收藏**【Claude 定】：`user_favorite` view 也會列出已下架的行程，收藏頁照樣顯示，但要做到三點：
  - 加上「已下架」標記。
  - 卡片不能點進行程頁，因為行程頁只會查上架中的行程。
  - 仍然可以取消收藏。

  理由：讓會員自己決定要不要清掉，不要讓收藏憑空消失。若錯，代價只是收藏頁多出一些灰掉的卡片。

## 6. 姓名規則

- 新增一個共用的姓名規則：去掉頭尾空白後長度為 2 到 20 個字，不能是空字串。註冊（`userInfo_Validator.js:4`）、會員資料（`userprofile_Validator.js:3`）、結帳收件人（`checkout_Vaildator.js:23`）三處都改用它，錯誤訊息統一。
- **Google 登入**（`controllers/userinfo.js:142`、`:202`）：去掉頭尾空白後，超過 20 字就截斷到 20 字；名字短於 2 字或沒有名字時，改用 email 的 `@` 前段，再截斷到 20 字【Claude 定】—— 理由：名字不合規則時，結帳頁會擋住 —— 若錯的代價：Google 會員看到的名字和 Google 帳號上的不一樣。
- 字數以 Unicode 字元計算（JavaScript 的 `[...s].length`），不是以 bytes 計算。
- 前端的註冊、會員資料、結帳表單也要改成相同的上下限。

## 7. P4 留下的項目

1. **折扣欄位清空**【Claude 定】：
   - 決定：訂單轉成逾時或取消時，同時清掉 `orders.discount_type` 和 `discount_price`。
   - 位置：expireIfOverdue 和 cancelPendingOrders，都是在本交易已經 FOR UPDATE 鎖住的那筆訂單上修改，屬於 `docs/lock-order.md` 的例外 A。

## 8. 測試（總 spec §4.2 四層）

- **API**：每個新端點都要測正常、分頁、未登入 401、admin 被擋、驗證錯誤的完整訊息。
- **安全**：
  - 越權讀取：會員 A 讀不到會員 B 的訂單、訂單明細、舊的已購買明細、點數紀錄，也刪不掉 B 的收藏，一律回 404。
  - 負點數：退款讓餘額變成負數之後，pointslevel 回傳 0。
- **DB 狀態**：
  - 重複收藏只有一筆；同時收藏同一個行程只有一筆。
  - 同時第一次加入購物車只產生一台購物車。
  - 通知設定 upsert 之後每個會員只有一筆。
  - 逾時或取消之後折扣欄位為 NULL。
  - V6 migration 在 seed 上可以正常套用。
- **E2E**：
  - P5 主線（§0）。
  - 通知設定存檔後重新整理，設定仍在。
  - 待付款訂單按「繼續付款」會導到付款頁。
  - 負點數會員的等級頁顯示 0 點。
  - Google 長名字：用 API 或 DB 準備資料即可，不需要真的走 Google 登入。
- **seed 帳號唯讀**的約束維持不變。需要寫入的測試一律自己建立會員。
